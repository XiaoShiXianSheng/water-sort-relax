- V6.0 的四个关键修复（都是上一版曲线的**真缺陷**，不是美化）：
  1. **阶段边界不再掉难度** —— 每段起点值 = 上一段终点值（旧版 L15→L16 密度 98.1→89.7，玩家读到「进了新阶段反而变简单」）；
  2. **50~90 关不再是平线** —— 操作量预算从「一律 150 步」改成**分段**（≤25 关 150 / ≤60 关 175 / 61~90 关 200 步）；
  3. **L19→L20 不再凭空多 13 格** —— 行数用 `floor`、列数用 `round`，错开「加一行」与「加一列」的时机；
  4. **天花板抬高到 17 色 / 17 管** —— 水管上限不再写死 7，改由屏幕宽 + `TUBE_MIN_W` 反推（旧版第 24 关就触顶）。

## 代码结构（全在一个文件里，按这一层的顺序读）

| 位置 | 内容 |
|---|---|
| `lv` 变量区 | 全局画布常量：`BOTT_Y`（管底基准线）、`SLOT_Y`（台面）、`GRID_Y0`（货架） |
| `levelPlan(lv, tier)` | **难度曲线核心（V6.0 重写）**。按 `STAGE_CURVE` 的 7 个阶段切片（教学 1~3 / 入门正式 4~8 / 正式挑战 9~15 / 高密度 16~25 / 困难 26~40 / 极限 41~60 / 极限+ 61~90），在段内按进度 `k∈[0,1]` 插值。三条不变量：**① 每段起点 = 上一段终点**（阶段边界不掉难度）；**② 行数用 floor、列数用 round**（错开「加一行」与「加一列」，避免单关凭空多 13 格）；**③ 校准③ 用分段预算 `moveBudgetFor(lv)` 削行削列**（≤25 关 150 / ≤60 关 175 / 61~90 关 200 步）。输出 `density` / `decisionDensityScore` 供测试与调参用 |

| `tubeCountFor(units, want)` | 水管根数自适应。上限**不再写死**，由 `maxTubesByWidth()`（屏幕宽 + `TUBE_MIN_W`）反推 → 高关能达到 17 根 |
| `genLevel(lv, opts)` | 关卡生成：解析档位（`opts.tier` > 每日挑战 > 热身/普通）→ 算格子布局 → 摆门洞/冰冻 → 分配瓶子 → 分配水层 → **可解性自检**（失败重试 40 次，兜底撤冰冻） |
| `resolveChallengeTier / inWarmup / warmupOnBoot / advanceWarmup` | **V6.0 §五-A 回归热身**：闲置超阈值 → 本次挑战从热身1 起步；通关逐档回升；进度字段一个字节都不碰 |

## 已知的设计取舍（欢迎挑战）

1. **保证不卡死**：生成期自检 + 运行时兜底（撤销/道具/复活），宁可重生成也不让玩家卡住。
   代价是「真失败率可能偏低 → 复活广告触发少」，这是本项目最大的商业化开放问题（见验收报告 §17）。
2. **平铺而非堆叠**：所有瓶子同层、开局全部可点（和《羊了个羊》的堆叠遮挡是两套机制）。
   代价是难度天花板受「同屏可读性」限制。**反直觉现象**：把关卡改大以后通关率反而升高 —— 因为格子和瓶子一起加，
   「开局可点占比」同步上升。**加格子加的是操作量，不是思考深度**（绕路比全关卡稳定在 2.2~2.4）。
   所以 V6.0 的取舍是：**格数在 54 格（9×6）封顶，晚局的难度增量全部来自「门洞 6→8 + 冰冻 6→8」**（纯思考量，不加时长）；
   同时把操作量预算按关卡分段放宽，让 61~90 关能真正比 41~60 关难，而不是撞在一条 150 步的平线上。
   完整数据见 `outputs/V6.0_关卡参数与难度报告.md` 与 `outputs/解压水消除_商业化上线验收报告.md` §12。
3. **回归热身是「另一条轴」，不是「降级」**：档位轴 `-2 热身1 → -1 热身2 → 0 普通 → 1 困难 → 2 极限` 有正有负。
   负档缩棋盘、正档只加约束，**「最高关卡 / 解锁进度」与「本次挑战档位」严格分开存** ——
   热身绝不写 `level` / `maxLevel`，这是「老玩家回来发现进度没了」这类事故的结构性防线。
4. **每瓶固定 3 口**：曾有 bug 让某些瓶子变 4 口，出现「1/4」这种分母，现在写死 `cap=3`，
   道具清掉的水直接倒进同色瓶保证守恒。
5. **没有构建、没有依赖、没有框架**：为了"拿走就能用"。代价是 5000+ 行挤在一个文件里。

### 四条铁律（踩过才写的）

- **每个新断言都必须做「回滚验证」**：故意把产品代码改坏 → 必须看到对应 FAIL → 改回来。
  已经自动化成 `node qa_rollback.js`（一条命令跑完 93 个用例，并且用 md5 校验原文件一定被还原）。
  这招在本项目抓到过**六次假绿**：断言找错对象、探针只点正中心、撤销断言没覆盖水管回滚、
  冰冻不变量在「走完帧之后」采样、门禁超时被当成「如期失败」、以及下面这条。
  > 一条断言建议配**多条**改坏用例：如果所有改坏都让同一簇断言一起红，
  > 你就分不清哪条断言真有独立效力。本轮「主循环守恒」配了 3 条用例，
  > 其中「喝掉的水不从管里扣」**只让守恒那条红**（瓶子照样收走），这才证明守恒断言不是搭便车的。
- **测试自己会污染被测状态**：功能套件开头有 400 次随机点击的冒烟测试，
  有约 27% 的概率点到「胜界面 → 挑战 → 困难」，把 `G.tier` 改脏 ——
  而 `genLevel(lv)` 不传 `opts.tier` 时会沿用 `G.tier`，于是后面一整簇「普通档」断言集体假 FAIL
  （20 次里挂 5 次，且挂的永远是同一簇）。修法是冒烟后显式还原 + 一条哨兵断言守住它。
  **随机乱点之后必须还原状态，否则它就是在给后面的断言埋雷。**
- **不要在同一文件并行改多处**：read-modify-write 竞态会静默丢改动。
- **涉及随机关卡的断言要用固定种子**（`withSeed`），否则同样一行代码两次跑出两个结果。
  机器人套件用的是固定种子，所以「1~40 关全通」是**确定性**条件，适合当门禁。

其他测试坑（`handleTap` 开场会落定喝水动画、构造"真死局"必须掏空货架等）见 [`QA_自测体系.md`](QA_自测体系.md)。
