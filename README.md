# 解压水消除（Water Sort Relax）

单文件 HTML5 休闲解压小游戏。目标：把水管里混杂的彩色水分装到同色瓶子，接满 3 口自动收走，收完所有瓶子通关。

- **线上**：https://water-sort-relax.app.workbuddy.host/
- **形态**：`outputs/解压水消除.html` 一个文件搞定，双击即玩，零依赖
- **技术**：纯 ES5（兼容老 WebView）· Canvas 2D · WebAudio 现场合成音效（无音频文件）
- **截图**：`screenshots/` 目录（旧版 9 张 + V4.0 九张 `v4_10~v4_18*.png`：首页 / 教学 / 普通对局 / 第30关 / 失败复活面板 / 三档面板 / 结算 / 提示条 / 选关）
- **自动测试**：399 项断言 / 7 个套件，一条命令跑完 → 见 [`QA_自测体系.md`](QA_自测体系.md) 与 [`qa_report.md`](qa_report.md)
- **上线门禁**：`node qa_run.js --gate` —— 10 条硬条件（0 FAIL / 无 flaky / 无崩溃 / 体积 / ES5 / 零依赖 / 1~40 关可解 / 机器人 1~40 全通 / 发布件==主文件 / **线上字节与本地一致**），不过就打印「禁止上线」并退出码 3
- **性能体检**：`node qa_perf.js` —— 真 Chrome headless 在 360×640 / dpr=1 下逐帧计时 → 见 [`qa_perf.md`](qa_perf.md)
- **商业化验收**：[`outputs/解压水消除_商业化上线验收报告.md`](outputs/解压水消除_商业化上线验收报告.md)（P0 18/18、P1 6/6、Money-OS 14 问逐项、上线条件结论）

## 这次想要的评审方向

**请优先看「能不能赚钱」和「能不能留住人」，不要纠结画面好不好看。**

一句话概括 V4.0 之后的现状（完整数据见 [`outputs/解压水消除_商业化上线验收报告.md`](outputs/解压水消除_商业化上线验收报告.md) §15/§17）：

- 广告只留 3 个场景（失败复活 / 工具补充 / 胜利后低频插屏），全部是玩家主动要或自然断点；
  但关卡生成仍做可解性自检 → **真失败率可能偏低 → 复活广告触发次数待真实数据验证**（核心矛盾没消失，只是从"架构上不可能触发"变成了"需要埋点回答"）
- 存档 / 星级 / 三档挑战 / 每日挑战都有了，但**没有推送、没有签到、没有社交 → 次日留存钩子仍然偏弱**
- 广告位没开通、`CFG.trackUrl` 留空 → **真实收入与真实触发率 = 0 数据，必须上线拿**

## 代码结构（全在一个文件里，按这一层的顺序读）

| 位置 | 内容 |
|---|---|
| `lv` 变量区 | 全局画布常量：`BOTT_Y`（管底基准线）、`SLOT_Y`（台面）、`GRID_Y0`（货架） |
| `levelPlan(lv)` | **难度曲线核心**。1~3 关教学（9格/3色/无门洞）、4~8 关过渡（每次只加一个复杂度）、9+ 关靠**决策密度**递进，每 5 关一个波浪周期。货架阶梯 9/12/15/18/20/24 格，**第 19 关起恒定 6 列 × 4 行 = 24 格、每行等长**（同一关开局形状完全确定）；26 是保留的硬上限 |
| `tubeCountFor(units)` | 水管根数自适应（**3~7 根，封顶 7**：原 9 根时最外 2 根完全出屏且点不到） |
| `genLevel(lv)` | 关卡生成：算格子布局 → 摆门洞/冰冻 → 分配瓶子 → 分配水层 → **可解性自检**（失败重试 40 次，兜底撤冰冻） |
| `buildGrid / cellAt / rowX0 / neighborCell` | 货架的「行长度表」布局。**第 19 关起格数恒为「列×行」（6×4=24），每行等长、开局无空格**；行长度表只是保留的通用容器（门洞不再靠多塞瓶子占格） |
| `layoutSolvable()` | 剥落式可解性自检：反复剥掉"此刻可取"的元素，剥不干净 = 存在依赖环 = 死锁 |
| `checkStuck()` | 运行时卡死判定。两级反馈：软提示条（持续 1 秒才提示）+ **真实失败面板 `enterFail()`** |
| `handleTap()` | 全部输入。**注意开场对 `G.anim` 的处理**——历史 bug："动画期间点击被吞"让玩家以为卡顿 |
| `useClear / useFinger / useSwap / doUndo` | 三个道具 + 撤销 |
| `AdService` | **商业化核心**：`Game → AdService → TestAdProvider / TapTapAdProvider`。频控/幂等/降级/埋点全在这层；`CFG.adUnit` 为空自动降级 TEST |
| `enterFail / rescueGrant / doRevive` | 真实失败 → 看广告复活 → **4 级兜底保证复活后必有合法决策**（开槽→快照→发工具→补互换） |
| `Store` | localStorage 存档：djb2 校验和 + 版本迁移 + 脏档重建 + 隐私模式静默降级 |
| `Track` | 埋点：本地缓冲 + `sendBeacon`，兜底 `new Image().src`（**刻意不用 fetch**，守"零外部依赖"红线） |
| `drawTube / drawTubeOpenPath` | 水管绘制（含水柱顶出屏幕的平口造型）· `drawJarCounter` 台面瓶子 + 三格进度刻度 |
| `render()` / 各 `draw*` | 绘制 |

## 已知的设计取舍（欢迎挑战）

1. **保证不卡死**：生成期自检 + 运行时兜底（撤销/道具/复活），宁可重生成也不让玩家卡住。
   代价是「真失败率可能偏低 → 复活广告触发少」，这是本项目最大的商业化开放问题（见验收报告 §17）。
2. **平铺而非堆叠**：所有瓶子同层、开局全部可点（和《羊了个羊》的堆叠遮挡是两套机制）。
   代价是难度天花板低 —— 机器人第 30 关 45% 一次通关，平均 200 步（V4.0 把它从 297 步压下来了）。
   **反直觉现象**：把关卡改大以后通关率反而升高 —— 因为格子和瓶子一起加，
   "开局可点占比"同步上升。**加格子加的是操作量，不是思考深度**（绕路比全关卡稳定在 2.2）。
   所以 V4.0 改为：格子硬上限 26（**稳态货架 24 格 = 6×4，第 19 关起恒定、每行等长**），难度靠决策密度而非棋盘尺寸。
   完整数据见 `outputs/解压水消除_商业化上线验收报告.md` §12。
3. **每瓶固定 3 口**：曾有 bug 让某些瓶子变 4 口，出现「1/4」这种分母，现在写死 `cap=3`，
   道具清掉的水直接倒进同色瓶保证守恒。
4. **没有构建、没有依赖、没有框架**：为了"拿走就能用"。代价是 3900+ 行挤在一个文件里。

### 四条铁律（踩过才写的）

- **每个新断言都必须做「回滚验证」**：故意把产品代码改坏 → 必须看到对应 FAIL → 改回来。
  已经自动化成 `node qa_rollback.js`（一条命令跑完 25 个用例，并且用 md5 校验原文件一定被还原）。
  这招在本项目抓到过**六次假绿**：断言找错对象、探针只点正中心、撤销断言没覆盖水管回滚、
  冰冻不变量在「走完帧之后」采样、门禁超时被当成「如期失败」、以及下面这条。
- **测试自己会污染被测状态**：功能套件开头有 400 次随机点击的冒烟测试，
  有约 27% 的概率点到「胜界面 → 挑战 → 困难」，把 `G.tier` 改脏 ——
  而 `genLevel(lv)` 不传 `opts.tier` 时会沿用 `G.tier`，于是后面一整簇「普通档」断言集体假 FAIL
  （20 次里挂 5 次，且挂的永远是同一簇）。修法是冒烟后显式还原 + 一条哨兵断言守住它。
  **随机乱点之后必须还原状态，否则它就是在给后面的断言埋雷。**
- **不要在同一文件并行改多处**：read-modify-write 竞态会静默丢改动。
- **涉及随机关卡的断言要用固定种子**（`withSeed`），否则同样一行代码两次跑出两个结果。
  机器人套件用的是固定种子，所以「1~40 关全通」是**确定性**条件，适合当门禁。

其他测试坑（`handleTap` 开场会落定喝水动画、构造"真死局"必须掏空货架等）见 [`QA_自测体系.md`](QA_自测体系.md)。
