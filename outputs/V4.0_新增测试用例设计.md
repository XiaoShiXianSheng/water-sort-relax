# 《解压水消除》V4.0 新增测试用例设计

> 作者：商业化调研与测试设计工程师（与核心开发 Agent 并行）
> 目标读者：核心开发 Agent（实现功能后按本文件补测试）+ 验收人
> 风格对齐：现有 `test_water.js`（Node 无头、`withSeed` 固定随机、`chk(name, ok)` PASS/FAIL、`DBG.*` 后门、`frames(n)` 推进动画）
> 原则：**所有用例必须可在 Node 环境直接 `node test_water.js` 跑通**，不依赖真实浏览器/真实广告 SDK；线上 SDK 一律用 TestAdProvider / mock 替身。

## 0. 后门契约（核心开发必须先暴露这些钩子，测试才能挂上）

现有 `test_water.js` 在注入点往 `window.__DBG` 上挂了一批函数。V4.0 新增模块（SaveManager / AdService / Analytics / 复活 / 档位 / 星级 / 每日挑战）**必须**按下面这张表把测试句柄暴露到 `__DBG`，否则下列用例无法执行。命名可与实现不同，但语义必须一一对应；若改名，请同步改本文件第 1~9 节代码里的 `DBG.xxx`。

| 后门 | 语义 | 必须暴露的理由 |
|---|---|---|
| `DBG.save` | SaveManager 模块本身（含 `save()/load()/setRaw()/reset()`） | 存档读写/损坏/迁移必须可直接调 |
| `DBG.ad` | AdService 单例（含 `showRewarded/showInterstitial/state/reset/setProvider`） | 广告全流程、频控、幂等要可驱动 |
| `DBG.adLog` | AdService 内部事件队列（`ad_request/ad_show/ad_complete/...`） | 验证发奖只在 complete 后 |
| `DBG.analytics` | Analytics 模块（含 `track(name,props)`、`events` 已发队列、`reset()`） | 埋点触发/参数/去重 |
| `DBG.revive` | 当前局复活相关状态（`reviveLeft/reviveUsed/snapshot/stuck`） | 复活次数限制、快照恢复 |
| `DBG.diff(level, tier)` | 取某关某档（normal/hard/hell）的难度参数 | 三档参数差异、单局步数 |
| `DBG.stars` | 星级计算函数 `computeStars(level, moves, toolsUsed, restarts)` | 1~3 星阈值 |
| `DBG.daily` | 每日挑战模块（`seedFor(dateStr)/result/record()`） | 固定种子、每日不同 |
| `DBG.tier` | 当前关卡档位状态（`currentTier/unlocked[level][tier]`） | 普通/困难/极限解锁 |
| `localStorage` 桩 | 测试启动时已在 `test_water.js` 浏览器桩里补一个内存版 localStorage | 存档不能真读浏览器 |

> 说明：现有 `test_water.js` 的浏览器桩（第 12~47 行）**还没有 localStorage**。请在桩里补一个内存版：
> ```js
> const _ls = {};
> global.localStorage = {
>   getItem: k => (k in _ls ? _ls[k] : null),
>   setItem: (k, v) => { _ls[k] = String(v); },
>   removeItem: k => { delete _ls[k]; },
>   clear: () => { for (const k in _ls) delete _ls[k]; },
>   _dump: () => _ls, _setRaw: (k,v) => { _ls[k] = v; }   // 注入损坏数据用
> };
> ```
> `_setRaw` 是测试专用后门：绕过 JSON 序列化，直接塞坏数据，用于"损坏数据恢复"用例。

## 1. 存档测试（SaveManager）

**目标**：保存/读取/损坏恢复/版本迁移/读取失败回退初始。对应 V4.0 §十六、§二十四。

### 1.1 保存并读回
- 前置：`DBG.save.reset()` 清空 localStorage；进入第 5 关，把道具改到 `{clear:2,finger:1,swap:0}`。
- 步骤：调 `DBG.save.save()` → 模拟重启（重新 `load()`）。
- 断言：读回的 `level===5`、`tools.clear===2`、`tools.finger===1`、`schemaVersion === CURRENT_VERSION`。
- 预期：round-trip 完全一致，无丢字段。

```js
// ============ 测试 5.1：存档保存/读回 ============
try {
  DBG.save.reset();
  DBG.gen(5); frames(6); settle();
  const G = DBG.G;
  G.level = 5; G.tools = { clear: 2, finger: 1, swap: 0 };
  DBG.save.save();
  const loaded = DBG.save.load();
  chk('存档：保存后读回关卡一致', loaded.level === 5);
  chk('存档：道具结余 round-trip 一致',
    loaded.tools.clear === 2 && loaded.tools.finger === 1 && loaded.tools.swap === 0);
  chk('存档：写入时带上当前 schemaVersion', loaded.schemaVersion === DBG.save.CURRENT_VERSION);
} catch (e) { console.error(e); chk('存档保存/读回套件执行', false); }
```

### 1.2 损坏数据恢复（JSON 非法）
- 前置：用 `localStorage._setRaw(KEY, '{###不是JSON###')` 塞一条坏数据。
- 步骤：`DBG.save.load()`。
- 断言：不抛异常、不白屏、返回值是安全初始档（`level===1`、道具为初始值、`schemaVersion===CURRENT_VERSION`）。
- 预期：坏档被吞掉并回退初始，而不是崩在 JSON.parse。

```js
// ============ 测试 5.2：损坏数据恢复 ============
try {
  localStorage._setRaw(DBG.save.KEY, '{{{### broken json ###');
  let threw = false, loaded = null;
  try { loaded = DBG.save.load(); } catch (e) { threw = true; }
  chk('存档：损坏 JSON 不抛异常、不白屏', !threw);
  chk('存档：损坏后回退到安全初始档（第1关/初始道具）',
    loaded && loaded.level === 1 && loaded.schemaVersion === DBG.save.CURRENT_VERSION);
} catch (e) { console.error(e); chk('损坏恢复套件执行', false); }
```

### 1.3 版本迁移（旧 schema 缺字段）
- 前置：手工塞一条 `schemaVersion = CURRENT-1` 的旧档（缺 `stars`、`challengeTier` 等新字段）。
- 步骤：`load()`。
- 断言：迁移后旧字段（level/tools）保留；缺失的新字段被补成默认值（`stars={}`、`challengeTier={normal:true,hard:false,hell:false}`），不出现 `undefined` 被存进 G。
- 预期：老用户升级不丢进度，新字段有安全默认。

```js
// ============ 测试 5.3：版本迁移 ============
try {
  const oldVer = DBG.save.CURRENT_VERSION - 1;
  localStorage._setRaw(DBG.save.KEY, JSON.stringify({
    schemaVersion: oldVer, level: 7, tools: { clear: 1, finger: 1, swap: 1 }
    // 故意缺 stars / challengeTier / dailyResult
  }));
  const loaded = DBG.save.load();
  chk('存档：旧档的旧字段（level/tools）不丢', loaded.level === 7 && loaded.tools.clear === 1);
  chk('存档：迁移后 schemaVersion 升到当前', loaded.schemaVersion === DBG.save.CURRENT_VERSION);
  chk('存档：缺失的新字段被补默认（stars/challengeTier）',
    loaded.stars && typeof loaded.stars === 'object' &&
    loaded.challengeTier && loaded.challengeTier[7] && loaded.challengeTier[7].normal === true);
} catch (e) { console.error(e); chk('版本迁移套件执行', false); }
```

### 1.4 读取完全失败时回退初始
- 前置：让 `localStorage.getItem` 抛错（桩里临时换成抛错函数）。
- 步骤：`load()`。
- 断言：仍返回初始档，不抛错到外层。
- 预期：任何异常路径都收敛到"安全初始"，绝不白屏。

```js
// ============ 测试 5.4：读取失败回退初始 ============
try {
  const origGet = localStorage.getItem;
  localStorage.getItem = () => { throw new Error(' quota/browser throw '); };
  let threw = false, loaded = null;
  try { loaded = DBG.save.load(); } catch (e) { threw = true; }
  localStorage.getItem = origGet;
  chk('存档：getItem 抛错时 load() 仍不向外抛', !threw);
  chk('存档：异常读取回退初始档', loaded && loaded.level === 1);
} catch (e) { console.error(e); chk('读取失败回退套件执行', false); }
```

## 2. 广告测试（AdService）

**目标**：Test Mode 全流程 / Online Mode 骨架 / 加载失败不发奖 / 中途退出不发奖 / 完成回调发奖 / 重复回调幂等 / 频控 / 重复发奖被拦。对应 V4.0 §四、§十二、§十三、§十四、§二十四。

> 关键设计约定：AdService 内部**绝不在 `showRewarded()` 同步路径里发奖**。发奖只能由 provider 回调 `onReward(placementId)` 触发，且必须带一个本局内的 `rewardToken`，AdService 用 `Set` 去重。TestAdProvider 用 `DBG.ad.fakeComplete()/fakeCancel()/fakeLoadFail()` 模拟回调。

### 2.1 Test Mode 完整流程
- 前置：`DBG.ad.setProvider('test')`；记录发奖前道具数。
- 步骤：`showRewarded('revive')` → TestAdProvider 立即 complete → 检查道具。
- 断言：Test Mode 下点击即完成、发奖成功、事件队列里有 `ad_request/ad_show/ad_complete/reward_granted` 各一次。
- 预期：开发/测试环境闭环可用。

```js
// ============ 测试 6.1：Test Mode 完整流程 ============
try {
  DBG.ad.reset(); DBG.ad.setProvider('test');
  const G = DBG.G; const toolsBefore = G.tools.clear;
  DBG.ad.showRewarded('revive');           // Test provider 立即 complete
  chk('Test Mode：showRewarded 后立即发奖（道具+1）', G.tools.clear === toolsBefore + 1);
  const ev = DBG.adLog.map(e => e.name);
  chk('Test Mode：事件含 request/show/complete/reward_granted',
    ev.includes('ad_request') && ev.includes('ad_show') &&
    ev.includes('ad_complete') && ev.includes('reward_granted'));
} catch (e) { console.error(e); chk('Test Mode 流程套件执行', false); }
```

### 2.2 Online Mode 骨架（不接真 SDK）
- 前置：`DBG.ad.setProvider('tap')`；TapTapAdProvider 在 Node 环境下没有真实 bridge。
- 步骤：`showRewarded('revive')`。
- 断言：不崩、不发奖、走 `ad_load_fail` 降级分支（因为 Node 里没有 `window.tt`/TapSDK bridge）；骨架存在，凭据为空时安全降级而不是把奖励白送。
- 预期：Online 只是骨架，等真实凭据/真机再激活。

```js
// ============ 测试 6.2：Online Mode 骨架安全降级 ============
try {
  DBG.ad.reset(); DBG.ad.setProvider('tap');
  const G = DBG.G; const toolsBefore = G.tools.clear;
  let threw = false;
  try { DBG.ad.showRewarded('revive'); } catch (e) { threw = true; }
  chk('Online Mode：无 bridge 时不抛异常', !threw);
  chk('Online Mode：加载失败绝不白送奖励', G.tools.clear === toolsBefore);
  chk('Online Mode：记录 ad_load_fail 事件', DBG.adLog.some(e => e.name === 'ad_load_fail'));
} catch (e) { console.error(e); chk('Online 骨架套件执行', false); }
```

### 2.3 加载失败不发奖
- 前置：TestAdProvider 配置为 `loadFails = true`。
- 步骤：`showRewarded('revive')` → provider 触发 `onError`。
- 断言：道具不变；事件为 `ad_request → ad_load_fail`；不出现 `ad_show/ad_complete/reward_granted`。
- 预期：V4.0 红线"加载失败不得发完整奖励"。

```js
// ============ 测试 6.3：加载失败不发奖 ============
try {
  DBG.ad.reset(); DBG.ad.setProvider('test', { loadFails: true });
  const G = DBG.G; const before = G.tools.clear;
  DBG.ad.showRewarded('revive');
  chk('加载失败：道具一分不多给', G.tools.clear === before);
  const names = DBG.adLog.map(e => e.name);
  chk('加载失败：有 ad_load_fail，且没有 show/complete/reward',
    names.includes('ad_load_fail') &&
    !names.includes('ad_show') && !names.includes('ad_complete') && !names.includes('reward_granted'));
} catch (e) { console.error(e); chk('加载失败套件执行', false); }
```

### 2.4 播放中途退出不发奖
- 前置：TestAdProvider 可正常 load，但用 `fakeCancel()` 模拟用户中途关闭。
- 步骤：`showRewarded('revive')` → `DBG.ad.fakeCancel()`。
- 断言：道具不变；事件含 `ad_cancel` 但不含 `reward_granted`。
- 预期：V4.0 红线"中途退出不得发完整奖励"。

```js
// ============ 测试 6.4：中途退出不发奖 ============
try {
  DBG.ad.reset(); DBG.ad.setProvider('test');
  const G = DBG.G; const before = G.tools.clear;
  DBG.ad.showRewarded('revive');
  DBG.ad.fakeCancel();                    // 模拟视频没看完就关
  chk('中途退出：不发奖励', G.tools.clear === before);
  chk('中途退出：记录 ad_cancel 事件', DBG.adLog.some(e => e.name === 'ad_cancel'));
} catch (e) { console.error(e); chk('中途退出套件执行', false); }
```

### 2.5 完成回调才发奖 + 2.6 重复回调幂等
- 前置：同一 `rewardToken`。
- 步骤：`showRewarded('revive')` → `fakeComplete()` 一次 → 再手动对同一 token 回调一次 `onReward`。
- 断言：第一次发奖 +1；第二次重复回调被拦截，道具不变成 +2；第二次事件应为 `reward_duplicate_blocked`。
- 预期：V4.0 红线"回调必须幂等，不能重复发奖"。

```js
// ============ 测试 6.5/6.6：完成发奖 + 重复回调幂等 ============
try {
  DBG.ad.reset(); DBG.ad.setProvider('test');
  const G = DBG.G; const before = G.tools.clear;
  DBG.ad.showRewarded('revive');
  chk('完成回调：发奖一次（+1）', G.tools.clear === before + 1);
  DBG.ad.replayLastReward();              // 故意把上次 complete 回调再喂一遍
  chk('重复回调：奖励不重复发（仍为 +1，不是 +2）', G.tools.clear === before + 1);
  chk('重复回调：记录 reward_duplicate_blocked',
    DBG.adLog.some(e => e.name === 'reward_duplicate_blocked'));
} catch (e) { console.error(e); chk('幂等发奖套件执行', false); }
```

### 2.7 频控生效
- 前置：`rewardedSessionCap = 3`、`interstitialSessionCap = 1`（配置化，V4.0 §十三）。
- 步骤：连续 `showRewarded` 成功 3 次后，第 4 次再请求。
- 断言：前 3 次正常发奖；第 4 次被频控拦截，不展示、不发奖、记录频控事件；插屏同理。
- 预期：广告不会无上限轰炸。

```js
// ============ 测试 6.7：会话频控 ============
try {
  DBG.ad.reset();
  DBG.ad.config({ rewardedSessionCap: 3, interstitialSessionCap: 1, interstitialCooldown: 5*60 });
  DBG.ad.setProvider('test');
  const G = DBG.G; const before = G.tools.clear;
  let granted = 0;
  for (let i = 0; i < 3; i++) { DBG.ad.showRewarded('revive'); }
  granted = G.tools.clear - before;
  chk('频控：会话前 3 次激励广告正常发奖', granted === 3);
  DBG.ad.showRewarded('revive');         // 第 4 次
  chk('频控：第 4 次被拦截，不再多发', G.tools.clear - before === 3);
  chk('频控：记录了被拦截的请求', DBG.adLog.some(e => e.name === 'ad_request_blocked'));
} catch (e) { console.error(e); chk('频控套件执行', false); }
```

### 2.8 奖励重复发放被拦截（业务层二次防护）

- 断言：第二次被业务层去重拦截。


## 3. 复活测试

**目标**：构造真实死局 / 失败面板出现 / 看广告后恢复安全快照 / 恢复后至少一个合法操作 / 复活次数限制。对应 V4.0 §九、§十、§十一、§二十四。

> 现有代码已有"卡死自救面板"雏形（test_water.js 测试 3.25）。V4.0 要把它升级成"真死局 → 面板 → 看广告 → 恢复安全快照 → 立刻可操作"。复活必须恢复到"最近安全快照"，而不是原地死局。

### 3.1 构造真实死局并弹失败面板
- 前置：参考现有 3.25 手法——把管底全设成场上无人认领的颜色，货架瓶全部 `gone`，只剩一个接不动的瓶；清空道具/撤销/解锁。
- 步骤：`waitIdle()` 等 `checkStuck` 生效。
- 断言：`G.stuck === true`，失败面板出现（V4.0 §十：失败反馈 + 看广告复活 + 重开 + 回首页）。
- 预期：死局是真实游戏逻辑产生的，不是人为恶心。

```js
// ============ 测试 7.1：真实死局 → 失败面板 ============
try {
  DBG.gen(6); frames(10);
  const G = DBG.G;
  G.slots.forEach(s => s.open = true);
  G.tools = { clear: 0, finger: 0, swap: 0 }; G.undoLeft = 0; G.unlockLeft = 0;
  G.tubes.forEach(t => { t.units = [7]; });          // 管底全是幽灵色 7
  const idle = G.bottles.find(b => b.col !== 7 && b.place !== 'gone');
  G.bottles.forEach(b => { if (b !== idle && b.place !== 'gone') b.place = 'gone'; });
  idle.place = 'counter'; idle.slot = 0; idle.fill = 0;
  waitIdle(); frames(30);
  chk('死局：无合法操作时 stuck=true 并弹失败面板', G.stuck === true && DBG.revive.panelOpen === true);
} catch (e) { console.error(e); chk('死局面板套件执行', false); }
```

### 3.2 看广告复活后恢复安全快照，且立刻有合法操作
- 前置：在 3.1 死局基础上，先做过至少一次真实操作（产生过安全快照）。
- 步骤：点面板"看广告复活" → Test Mode 自动 complete。
- 断言：复活后 `G.stuck === false`；棋盘状态回退到快照（不是原地死局）；**存在至少一个可上台面/可倒水的合法操作**（V4.0 §十一最终验收红线）。
- 预期：看完广告必须能继续玩，不能回到死局。

```js
// ============ 测试 7.2：复活恢复安全快照 + 至少一个合法操作 ============
try {
  DBG.gen(6); frames(10); settle();
  const G = DBG.G;
  G.slots.forEach(s => s.open = true);
  const seed = G.bottles.find(b => DBG.gridPlayable(b));
  if (seed) { click(seed.x, seed.y - 20); waitIdle(); frames(40); }  // 产生安全快照
  // 再把局面彻底搞死
  G.tools = { clear: 0, finger: 0, swap: 0 }; G.undoLeft = 0; G.unlockLeft = 0;
  G.tubes.forEach(t => { t.units = [7]; });
  const idle = G.bottles.find(b => b.col !== 7 && b.place !== 'gone');
  G.bottles.forEach(b => { if (b !== idle && b.place !== 'gone') b.place = 'gone'; });
  idle.place = 'counter'; idle.slot = 0; idle.fill = 0;
  waitIdle(); frames(30);
  chk('复活前：确实处于死局', G.stuck === true);
  DBG.ad.setProvider('test');
  DBG.revive.watchAd();                       // 点「看广告复活」→ Test complete
  waitIdle(); frames(20);
  chk('复活后：stuck 解除', G.stuck === false);
  const legalMove = G.bottles.some(b => DBG.gridPlayable(b)) ||
                    G.bottles.some(b => b.place === 'counter' && b.fill < b.cap);
  chk('复活后：至少存在一个合法可操作（V4.0 §十一红线）', legalMove);
} catch (e) { console.error(e); chk('复活恢复快照套件执行', false); }
```

### 3.3 复活次数限制
- 前置：`reviveLimit = 1`（每局限复活 1 次）。

## 4. 难度测试

**目标**：1~3 关参数简单 / 4~8 关递进 / 9 关后决策密度增长 / 三档参数差异 / 单局步数合理。对应 V4.0 §五、§六、§八、§二十四。

> 现有 `levelPlan(level)` 已定义格子数波浪（测试 4）。V4.0 新增：每关按 tier（normal/hard/hell）取参数，且难度增长靠"决策密度"而非单纯堆格子。

### 4.1 1~3 关参数简单
- 前置：取 `DBG.diff(1..3, 'normal')`。
- 断言：颜色数 ≤3、可用台面槽充足、无冰冻/门洞干扰（或极少）；机器人用很少步数通关。

```js
// ============ 测试 8.1：1~3 关参数简单 ============

    const p = DBG.diff(lv, 'normal');
    chk('第 ' + lv + ' 关：颜色数≤3（新手关）', p.colors <= 3);
    chk('第 ' + lv + ' 关：无冰冻/门洞干扰', p.ice === 0 && p.gates === 0);

} catch (e) { console.error(e); chk('新手关参数套件执行', false); }
```

### 4.2 4~8 关递进
- 前置：取 `diff(4..8,'normal')`。
- 断言：颜色数/干扰数随关卡单调上升（允许小波动，但整体 8 关 > 4 关）；逐步引入门洞/冰冻。
- 预期：不突然堆大量颜色，渐进复杂。

```js
// ============ 测试 8.2：4~8 关递进 ============
try {
  const c4 = DBG.diff(4, 'normal').colors, c8 = DBG.diff(8, 'normal').colors;
  const g4 = DBG.diff(4, 'normal').gates + DBG.diff(4, 'normal').ice;
  const g8 = DBG.diff(8, 'normal').gates + DBG.diff(8, 'normal').ice;
  chk('4~8 关：颜色数整体上升（8 关≥4 关）', c8 >= c4);
  chk('4~8 关：干扰（门洞/冰冻）逐步引入', g8 > g4);
} catch (e) { console.error(e); chk('中段递进套件执行', false); }
```

### 4.3 9 关后决策密度增长（而非单纯堆格子）
- 前置：对比 `diff(9)` 与 `diff(15)`、`diff(20)`。
- 断言：9 关后，"决策密度"指标（如：可选分支数、空间约束比、死局风险项）增长；格子数可以波浪起伏（V4.0 §五：不允许只做 3→4→5→6 色）。
- 预期：难度来自组合（颜色+空瓶+门洞+冰冻+排列），不是线性加色。

```js

```

### 4.4 普通/困难/极限三档参数差异
- 前置：取同一关 `diff(10,'normal'/'hard'/'hell')`。
- 断言：三档参数严格递进——hard 比 normal 空间更少/干扰更多；hell 比 hard 容错更低/死局风险更高；三档的"可用台面槽 normal≥hard>hell"。
- 预期：V4.0 §七三档差异化可被机器验证。


### 4.5 单局步数在合理范围

- 断言：新手关步数 ≤ ~40；普通关 ≤ ~120；高难关 ≤ ~200；不出现数百步/9~10 分钟局（V4.0 §八）。

**目标**：每个核心事件至少触发一次 / 参数完整 / 不重复触发。对应 V4.0 §二十一、§二十四。
