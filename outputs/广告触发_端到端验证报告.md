## 1. D1：真浏览器端到端实测（核心）

**怎么跑的**：真 Chrome 154（`--remote-debugging-port=9222`），用 CDP `Input.dispatchMouseEvent` 投**真鼠标按下/抬起**（不是直接调函数），坐标由游戏自己的 `view()` 变换从「720×1280 设计稿虚拟坐标」换算成 CSS 坐标——和玩家手指戳下去是同一条路径。

### A 组：默认地址（strict 线上同口径）· 真 Chrome

```
########## 场景 A：默认地址（strict / 无 sdk=real），真 Chrome ##########
[A1] PASS 进第 1 关后道具/撤销初始额度
     实测: state=play level=1 tools={"clear":1,"finger":1,"swap":1} undoLeft=5
[A2] PASS 点底部「万能指」把它消耗掉
     实测: tools.finger 1 → 0（点击后 tools={"clear":1,"finger":0,"swap":1}）
[A3] PASS 「万能指」用光后再点 → 走广告 → 次数 +1
     实测: tools.finger 0 → 1；埋点序列 = ad_request → ad_show → ad_complete → reward_granted
[A4] PASS 「魔法清除」用光
     实测: tools.clear 1 → 0
[A4b] PASS 「魔法清除」用光后再点 → 广告 → 次数 +1
     实测: tools.clear 0 → 1；埋点 = ad_request → ad_show → ad_complete → reward_granted
[A5] PASS 「随心互换」用光
     实测: tools.swap 1 → 0
[A5b] PASS 「随心互换」用光后再点 → 广告 → 次数 +1
     实测: tools.swap 0 → 1；埋点 = ad_request → ad_show → ad_complete → reward_granted
```

**用户要的那条链：`万能指 1 → 0 → 1`，肉眼可见的实测输出：**

```
点「万能指」前：    G.tools = {"clear":1, "finger":1, "swap":1}
点一次（消耗）：    G.tools = {"clear":1, "finger":0, "swap":1}     ← 1→0
再点一次（广告）：  G.tools = {"clear":1, "finger":1, "swap":1}     ← 0→1 ✅
埋点 = ad_request → ad_show → ad_complete → reward_granted
```

**「魔法清除」「随心互换」同样跑出 1→0→1**，三条道具都验过，不是拿一条代表。

> **这里必须说清一层**：A 组是在**没有 tap 的普通浏览器**里，环境自动降级成 `env='test'`，A3 那条 `ad_show → ad_complete → reward_granted` 是**模拟广告**链路（产品里的 Test 模式），不是真机真实广告。它证明的是**UI 链路通**：按钮 → 用光 → 广告流程 → 发奖 → 次数回来。真实广告素材要 C 组 + 真机。

### B 组：`?sdk=real` 且没有 tap（堵假绿的证据）

```
[B1] PASS ?sdk=real 无 tap：降级原因要写清楚，且**广告 Reward 账**必须不发（堵假绿）
     实测: degradeReason="no-real-runtime"；埋点 = ad_request → ad_show → ad_no_real_sdk → ad_fallback_granted
           AdService.stats.rewarded=0（无 reward_granted）
```

**假绿确实堵住了**：`ad_no_real_sdk` 打出来了，`reward_granted` 一条都没有，`stats.rewarded=0`。后台数据里一眼能分「没弹出来」和「弹出来了」。

### C 组：`?sdk=real` + 注入 mock tap（第③层，模拟 TapTap 容器）

```
[C1] PASS ?sdk=real + tap 存在（env=online）：点用光的道具 → 真 SDK 建实例 → show → onClose(isEnded) → 发奖 +1
     实测: tools.finger 1 → 0 → 1
           埋点 = ad_request → ad_show → ad_complete → reward_granted
           tap 调用链 = createRewarded:1067564 | rewarded:show
```

⚠ 这条是 **mock 顶替**的：只证明 `showRewarded → _tapRewarded → createRewardedVideoAd → show → onClose(isEnded) → _grant` 这条真机代码链路是通的，不证明那是有收益的真广告。

### D 组：插屏广告（你要的「弹窗广告」）

```
[D1] PASS 连胜不足（wins=0）→ 插屏被 gate 拦下，不进 show
     实测: showInterstitial 返回 false(拦截)；埋点 = ad_interstitial_blocked
[D2] PASS 调参后（interstitialAfterWins 3→0）插屏链路真的走到 tap show
     实测: showInterstitial 返回 true(放行)；埋点 = ad_show → ad_interstitial_close
           tap 调用 = createInter:1067565 | interstitial:show
     ⚠ 注：D2 是**调参触发**（interstitialAfterWins 3→0），不是 3 连胜自然触发；300s 冷却用 lastInter 回拨绕过。
[D3] PASS wins=3（满足 interstitialAfterWins=3）→ 插屏放行
     实测: showInterstitial 返回 true(放行)；埋点 = ad_show → ad_interstitial_close
[D4] PASS 单会话插屏上限触顶后不再放
     实测: session.inter=1 时返回 false(拦截)；埋点 = ad_interstitial_blocked
```

`interstitialAfterWins=3` + `interstitialSessionCap=1` + 300s 冷却这个组合是**刻意保守**的：一局最多来一次插屏，且要连赢 3 局。**「连胜 3 关自然弹出」这条全链路，真机连赢 3 关才能验，我没有用它做结论。**

### 真浏览器 CDP 端到端合计：**14 PASS / 0 FAIL**，连跑 3 次结果一致（无 flaky）

## 3. D3：两条观测面缺陷的判定

### 3.1 G8c 假 PASS —— **是真缺陷，而且当场抓到一个活的**

复现结果（`_probe_zip.js` 拆包实测）：

```
主文件：186600B  md5 65ad2ad270cf9ef704188feca77c90ea

=== tap_upload_v6.4.0.zip ===
  条目名: game/index.html | game/icon_512.png | game/UPLOAD_NOTES.txt
  门禁找的 'index.html'      → ❌ 找不到（门禁就是这么写的）
  实际写的是 'game/index.html' → {"size":181239,"md5":"e43470342d8bfbbf36639372433bc958"}
  包内 md5 与主文件一致 = false        ← ⚠ 旧版本包

=== tap_upload_v6.4.1.zip ===
  包内 game/index.html → {"size":186600,"md5":"65ad2ad270cf9ef704188feca77c90ea"}
  包内 md5 与主文件一致 = true
```

- **成因**：`qa_gate.js` 的 `zipEntry(buf,'index.html')` 按**全等**匹配条目名，`pack_zip.js` 写的是 `game/index.html` → 一条都读不到 → 落进 `zipSkip` → `zipBad.length===0` → 判 PASS。
- **优先级：高**。这不是「观测不准」，是**门禁空转**：它一个字节都没比对过，却报绿。真实后果就是你说的「上传包版本漂移它抓不住」——而**现在已经有一个活的实例**：`tap_upload_v6.4.0.zip` 里是旧版（181239B / `e4347034…`），门禁今天照样报 PASS。旧包没广告位 ID，一旦被重新打包/上传就是又一次「跑真广告零收益」。
- **建议改法（已改）**：`qa_gate.js` 里 `if (name === wantName)` → `if (name === wantName || name.split('/').pop() === wantName)`（路径末段匹配），一行，只动门禁脚本、没碰产品。
- **改完立刻现形**：

```
FAIL [G8c] 所有上传包内的 index.html 与主文件一致 → 已核对：tap_upload_v6.4.1.zip（186600B md5 65ad2ad2…）
     ❌ 版本不一致：tap_upload_v6.4.0.zip（包内 md5 e43470342d8bfbbf36639372433bc958 ≠ 主文件 65ad2ad2…）
=== 门禁本地条件：10 PASS / 1 FAIL ===
```

> ⚠ **这个红是我故意留下的，需要你拍板**：G8c 修好后变红，原因不是门禁代码错，是 `outputs/tap_upload_v6.4.0.zip` 里真的装着旧版。两个处理项（**我都没动，是你的决定**）：
> 1. 把 `tap_upload_v6.4.0.zip` 挪进 `outputs/_archive_旧版上传包/`（该目录已存在）；或
> 2. 重新打一次包覆盖它。
>
> 我**没有**删/挪任何上传包——那是你的交付物。

### 3.2 `ad_show` 误判 —— **是真缺陷，建议 P2，本轮先不改**

- **复现**（B 组真浏览器实测埋点）：`?sdk=real` + 无 tap → `ad_request → ad_show → ad_no_real_sdk`。
- **判定**：真缺陷，但**只污染观测面，不动发奖逻辑**（`stats.rewarded=0`、`reward_granted` 一条没有，发奖账是干净的）。危害是「看到 ad_show 就以为广告弹出来了」——恰恰是这次想分清的那件事。
- **优先级：中低（P2）**。**建议本轮不改**，理由：改产品 → 本地 md5 变化 → 已上线的 V6.4.1 与本地漂移 → **G8b 立刻转红**，等于逼着再来一次部署（你说了上线由你决定，我不该顺手制造一次漂移）。
- **建议改法（给下个版本，一行，两选一）**：
  - **推荐 R-A（一行，不动既有埋点顺序）**：`showRewarded` 里打 `ad_show` 那句加守卫 —— `forceRealSdk` 且 `!hasTap()` 时不打 `ad_show`。
  - R-B（把 `ad_show` 挪到 `_onlineRewarded` 里 `ad.show()` 之后）更准，但会改变线上链路的埋点顺序，`qa_biz.js:69` 那条「埋点齐全 ad_request/ad_show/ad_complete/reward_granted」会连坐变红，牵连面更大。
- **为什么不用 R-B**：`qa_biz.js` 那条埋点断言依赖 test 路径的 `ad_show`，挪走会把它打红，属于扩大改动范围。R-A 只在「确定没有真 SDK」时少打一条，其余场景埋点一个不差。

### 3.3 附带发现（工程侧没报，我实锤的）

**`?sdk=real` 无 tap 时，道具仍会 +1**（B2 观测项）：

```
[B2] OBS ?sdk=real 无 tap 时道具仍会经 fallback +1（不是发奖，是 adFailFallback:"free" 兜底）
     实测: tools.finger 0 → 1；埋点含 ad_fallback_granted
```

- 走的是 `refillTool` 的 **fallback 回调**（`adFailFallback:'free'`），`_fail()` 里 `opts.onFallback()` → `G.tools[id]++`，并给一句「暂时没有广告，直接补你 1 次」。
- 所以**假绿堵住了「广告奖励账」，没堵住「玩家白得一次道具」**。埋点诚实（`ad_no_real_sdk` + `stats.rewarded=0`），但**玩家侧确实拿到 +1**。
- 我的判定：**这不是 bug，是既定兜底策略**（广告拉不到不卡流程，对留存友好；代价是广告位拿不到收入也不卡人）。但**和「?sdk=real 无 tap 不发奖」这句验收口径不是一回事**，得跟老张说清楚，别让他以为「堵假绿 = 没网也拿不到道具」。
- **建议**：当作产品决策征询文策渊/主理人，本轮**不改动**（改动要重新部署）；若要改，`refillTool` 的 fallback 分支里去掉 `+1` 即可，一行。
