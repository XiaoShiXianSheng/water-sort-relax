## 0. 先读这一节：两个开关，别改错字段名

我在代码里逐行核对过，**你之前听说的 `CFG.AD_MODE` 这个字段名是错的**，代码里不存在。真正在 `outputs/解压水消除.html` 第 134~146 行的配置长这样：

```js
var CFG={
  env:'test',                              // ← 总开关：'test' | 'online'（不是 AD_MODE）
  adUnit:{rewarded:'',interstitial:''},    // ← 广告位 ID，填了就走真实广告
  rewardedSessionCap:3,
  interstitialSessionCap:1,
  interstitialCooldown:300,
  firstSessionProtection:15,
  interstitialAfterWins:3,
  reviveLimit:2,
  adFailFallback:'free',
  trackUrl:'',                             // ← 埋点上报地址，留空=只写本地
  trackLocalCap:80
};
```

**当前默认值（出厂状态）：**

| 字段 | 当前值 | 含义 |
|---|---|---|
| `CFG.env` | `'test'` | 模拟广告，不产生真实收入，也不会卡流程 |
| `CFG.adUnit.rewarded` | `''` 空 | 激励视频广告位 ID |
| `CFG.adUnit.interstitial` | `''` 空 | 插屏广告位 ID |
| `CFG.trackUrl` | `''` 空 | 埋点只落 `localStorage['wsr_ev']`，不上报 |

**降级逻辑（代码第 271~281 行，已实测）：** `env='online'` 时，如果运行时没有 `window.tap` 对象 → 自动退回 test（原因 `no-tap-runtime`）；如果有 `tap` 但 `adUnit.rewarded` 是空 → 也自动退回 test（原因 `no-ad-unit-id`）。**不会白屏，不会卡死。**

**URL 强制切换（调试用，代码第 147~152 行）：** 访问时加 `?ad=online` 或 `?env=online` 强制线上；`?ad=test` / `?env=test` 强制测试。真机验证时不要靠改代码，用这个更快。

### 3.4 改完怎么验证（照着做，别跳步）

**第 1 步：确认没降级**
在真机（TapTap App 内）打开游戏，用调试方式看 `AdService.env` 的值：
- 如果 = `'online'` → 广告位 ID 生效了 ✅
- 如果 = `'test'` 且 `AdService.degradeReason='no-tap-runtime'` → 说明不是跑在 TapTap 小游戏运行时里（比如你在普通手机浏览器打开的，那是**必然**的，正常）
- 如果 = `'test'` 且 `degradeReason='no-ad-unit-id'` → **`adUnit.rewarded` 没填进去，回去检查第 3.3 步**

**第 2 步：看一次真实激励视频**
故意玩到失败 → 点「看广告复活」：
- 应该弹出真实广告（不是模拟的）
- 看完 → 复活成功，回到可玩局面
- **中途退出** → 不发奖，提示"要看完整段广告才算数哦"

**第 3 步：看一次真实插屏**
连胜 3 局以上后，通关结算时可能弹一次插屏。
> 插屏有频控：单会话最多 1 次、冷却 300 秒、开局前 15 秒不弹、需连胜 3 次才解锁。**所以"打了一局没弹"是正常的，不是坏了。**

**第 4 步：验证埋点**
手机浏览器 / 调试工具里读 `localStorage['wsr_ev']`，应该能看到事件数组。

### 3.5 埋点上报地址（`CFG.trackUrl`）

现在留空 = 只写本地缓冲，**你拿不到任何线上数据**。

- **不填**：能上线，能过审，但第 5 节的 72 小时观察**基本没法做**（只能靠玩家口碑和后台的日活/时长）
- **填**：需要一个能接收 POST 的端点。代码用 `navigator.sendBeacon` 发 JSON，兜底用 `new Image().src` 发 GET 查询串（参数名 `e`）。

> ⚠️ 跨域/CORS：sendBeacon 的 POST 不受 CORS 限制；Image 信标是 GET，也不受。**但你得自己有个能收的端点。** 自建一个极简的收集服务，或者用第三方统计。具体选型我不推荐，别踩"上报地址把玩家数据发给不合规第三方"这个坑。

## 5. 上线后 72 小时观察清单

### 5.1 能直接看的（代码里已有埋点）

代码里有 **26 个埋点事件**（`Track.log(...)`）。**前提是 `CFG.trackUrl` 填了**，否则只能读本机 `localStorage['wsr_ev']`，线上数据拿不到。

**第一优先级：广告链路是否真的通**

| 盯什么 | 用哪些事件 | 正常是什么样 | 异常信号 |
|---|---|---|---|
| 广告有没有被请求 | `ad_request` | 有量 | 0 条 = 玩家根本没走到触发点，或按钮没露出来 |
| 能不能加载出来 | `ad_load_success` vs `ad_load_fail` | success 明显多于 fail | **`ad_load_fail` 占比过高 → 广告位没提审正式计费 / 填充率差**，去平台后台查 |
| 看完率 | `ad_complete` vs `ad_cancel` | complete 占多数 | cancel 过多 → 广告太长或触发时机惹人烦 |
| **有没有真发奖** | `reward_granted` | 应≈ `ad_complete` | 明显少于 = 发奖逻辑有问题，**这是 P0 事故** |
| 重复发奖 | `reward_duplicate_blocked` | 应该 ≈ 0 | 持续 >0 = 幂等失效，玩家在刷奖励 |
| 频控有没有误伤 | `ad_cap_blocked` | 少量正常 | 大量 = `rewardedSessionCap:3` 太紧，考虑放宽 |
| 插屏有没有乱弹 | `ad_interstitial_blocked` / `ad_interstitial_close` | blocked 应该远多于 close | close 过多 = 太频繁，玩家会骂 |
| 广告失败兜底 | `ad_fallback_granted` | 少量 | 大量 = 广告拉取环境差，注意别变成"白送道具"漏洞 |

**第二优先级：玩家有没有在玩**

| 盯什么 | 用哪些事件 | 说明 |
|---|---|---|
| 新增 / 启动 | `first_open` / `game_start` | `first_open` 是首次打开 |
| 次日回访 | `return_open` | **这是留存的唯一直接信号**，V4.0 没有推送/签到/社交，这一项大概率不好看 |
| 关卡进度分布 | `level_start` / `level_complete` / `level_fail` / `level_exit` | 看玩家卡在第几关、在哪关流失 |
| 单局时长 | `session_duration`（参数 `sec`, `level`） | 看是否真的 6~7 分钟那么长 |
| 复活广告到底触发多少次 | `revive_granted` / `revive_tool` | **这是本项目最大的商业开放问题**：关卡生成做了可解性自检 → 真失败率可能偏低 → 复活广告触发少。上线后第一个要回答的就是它 |
| 道具使用 | `tool_use`（参数 `tool`: clear/finger/swap） | 看哪个道具最受欢迎 |
| 每日挑战 | `challenge_start` / `challenge_complete` | 留存钩子之一 |

### 5.2 需补埋点才能看的（现在没有）

| 想看什么 | 现在缺什么 | 备注 |
|---|---|---|
| 崩溃率 / 白屏率 | ❌ 无 `error` / `fatal` 事件（代码里有 `fatalShown` 但没埋点） | **建议补**：这是上线后最该有的一个 |
| 广告收入 / eCPM / 填充率 | ❌ 代码侧不可能有 | 只能去 TapTap / 媒体平台后台看 |
| 分享 / 邀请 | ❌ 没有（V4.0 明确删掉了假分享） | 想做真分享需服务端模板审核 |
| 渠道来源 | ❌ 无 `utm` / `channel` 字段 | 想算 CAC 必须补 |

### 5.3 什么情况回滚

**立即回滚（不停服处理，直接退回 TEST）：**

1. **`reward_granted` 远少于 `ad_complete`** → 玩家看了广告没拿到奖励 → 差评风暴
2. **`reward_duplicate_blocked` 持续大量** → 奖励可被刷，经济崩了
3. **崩溃/白屏投诉集中出现**（应用商店评论 + 后台反馈）
4. **广告相关的差评占比突然飙高**（"一直弹广告""广告关不掉"）
5. **平台后台告警**（广告位违规 / 被封）

**观察但不回滚（记进待办，下个版本改）：**

- 次日留存低（这是 V4.0 已知的短板，不是事故）
- 复活广告触发率低（已知的开放问题，需要数据积累）
- eCPM 不理想（商业调优，不是事故）

### 5.4 回滚动作（代码侧 2 步）

**只改 `CFG`，不动任何游戏逻辑，风险极低：**

```js
var CFG={
  env:'test',                              // ← online → test，回到模拟广告
  adUnit:{rewarded:'',interstitial:''},    // ← 清空，彻底断掉真实广告
  ...
};
```

然后：
```bash
cp outputs/解压水消除.html publish_water/index.html
cd publish_water && zip -r ../解压水消除_v4.0.0_hotfix.zip index.html
```

**改这两行之后：** 所有广告走模拟流程，看完照样发奖（不会卡玩家流程），**不产生真实收入**。游戏本体不受影响。

> 📌 **更快的应急手段**：如果平台支持 URL 参数透传，先加 `?ad=test` 强制降级，不用重新打包。但这取决于平台怎么加载你的页面，**需确认**。

**回滚后必做：**
- [ ] 确认线上版本确实是 test（读 `AdService.env`）
- [ ] 去平台后台看广告位状态，必要时暂停
- [ ] 记录事故时间线：什么时候发现 / 影响多久 / 多少玩家
- [ ] 定位是**代码问题**还是**广告位配置问题**——这两类修法完全不同

## 6. 版本号与变更日志建议

### 6.1 版本号方案

**建议：`V4.0.0`**

理由：内部开发口径一直是 V4.0（提示词、验收报告、git 提交全是 V4.0），对外第一个上架版本就用 `4.0.0`，避免"内部 V4.0 / 对外 V1.0"这种对不上的混乱。

- `4.0.x` — 热修 / 广告位配置 / 文案调整（不动玩法）
- `4.x.0` — 新增内容（关卡、道具、活动）
- `5.0.0` — 玩法大改或商业化结构变化

> ✅ **已于 2026-09-28 补上**：`CFG` 第一行现在是 `version:'4.0.0'`，且每条埋点事件都带 `v` 字段（`Track.log` 的 `ev.v`）。上线后能从埋点里区分版本，出事时对得上号。
